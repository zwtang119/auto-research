## 0. 项目背景与目标

用户提供 predictionarena.ai 的 agent 成交数据（两组 "Last 50 Trades"），提出四个原始问题：
1. 押注信息能否指导下注（时延 / 效率）？
2. 能否构建 Agent 追踪（模拟盘）？
3. 能否上 GitHub 做时间存证？
4. 上 GitHub 如何信息最小化、避免泄露商业机密（只给结论、不给过程）？

**经多轮讨论，目标收敛为**：
- 对预测市场的问题**公开披露我们的 Yes/No 方向** → 市场结算后**归集最终答案** → 对外**宣传正确率**，作为互联网营销活动。
- 本质是**公开的预测 track record / 模拟盘**（不涉及真实资金）。
- **商业机密 = 方法**（如何从信号推导出 Yes/No）；预测方向与正确率必须公开（营销资产），方法永不公开。

## 2. 决策记录（按讨论时间线）

### 2.1 原始问题 Q1：押注信息能否"指导下注"？
- **结论**：作为**实时跟单信号 → 差**；作为 **agent 策略研究信号 → 有价值**。
- **理由与依据**：
  - **时延**：数据为 "Last 50 Trades" 滚动尾巴窗口 + 相对时间戳（36m~4h），无可见公开 API；爬页面再叠延迟。预测市场快，成交进 tracker 时价格已滑到 agent 入场价。
  - **效率**：预测市场整体有效（Kalshi 量 ~$25.9B，IOSG 数据）；AI agent 是市场参与者非神谕。跟单 suffer **逆向选择**（看到的是执行后的尾单）+ **幸存者偏差**（只看到最近 50 笔，无完整 PnL）。
  - **数据完整性红旗**：ticker 写 `26JUL24`（似 2024）而题面为 "Jul 24, 2026"，当前恰为 2026-07-24 → 新鲜度未验证，拿去跟单危险。
  - **方向性偏斜**：数据集 1 为 100% Buy NO（某 session/过滤视图），非均衡信号。
- **用户倾向**：未就 Q1 单独拍板，但整体接受"作为研究信号有价值、作为跟单信号不可用"的定性结论，并进入后续构建讨论。

### 2.2 分支 A — 数据源
- **用户选择**：**页面爬取**（非官方 API / 非手动粘贴）。
- **理由与依据**：用户要自动化持续追踪；predictionarena.ai 无可见公开 API，爬页面是唯一自动化路径。
- **用户倾向说明**：偏好自动化、可定时运行，而非手工粘贴。
- **附加警示（已记录）**：爬取可能触 arena 的 robots.txt / ToS（规模化再分发风险）；动手前需核查，必要时退回手动粘贴 + 仅本地/私有存证。

### 2.3 分支 B — 仓库可见性（首版 · ⚠️ 已被 2.7 取代）
- **用户选择**：**混合（公开 trades 仓 + 私有 conclusions 仓）**，并要求详细解释。
- **理由与依据**：公开仓发"观察到的成交"（公开事实，本就是公开记录），私有仓锁"结论/方法"。observation layer 与 reasoning layer 分离。
- **用户倾向说明**：明确倾向"混合"，且希望把"信息最小化"机制讲透——反映出用户对**泄密面**的高度敏感。

### 2.4 分支 C — 公开层信息粒度（首版 · ⚠️ 已被 2.7 取代）
- **用户选择**：**只发 `ticker + side + price + qty + ts + 伪名 agent`，结论标签一句话**。
- **理由与依据**：最小化暴露；agent 名哈希伪名化，连"重点盯哪几个 agent"都不暴露。
- **用户倾向说明**：极致最小化，只要结论不要过程。

### 2.5 分支 D — 爬取频率 + 去重
- **用户选择**：**一小时爬取一次**。
- **理由与依据**：每小时轮询 + 去重键 `(alias, ticker, side, price, qty, ts)` 足够研究用途；tracker 时延 ≈ 1h。
- **附加警示（已记录）**：trailing-50 滚动窗口在忙时会滑单——两帧间滑出的成交**永久丢失**，去重救不回。故拿到的是**抽样记录**非完整账本。
- **用户倾向说明**：选中等频率（非 5–15min 密轮询、非日终批量），在成本与覆盖间取平衡。

### 2.6 关键担忧 — 比特币哈希会不会暴露我们在追踪？（⚠️ 此节讨论的 OTS 方案已于 2.11 弃用，仅保留作当时风险分析）
- **用户担忧**：用 OpenTimestamps / 比特币交易哈希，会不会被人发现我们在追踪 predictionarena.ai？
- **澄清结论**：**不会**。OTS 仅把文件哈希写进比特币 `OP_RETURN`，**从不上链内容、不暴露身份**；OTS 证明"存在"不证明"作者"。
- **真正暴露面（纠正误区）**：
  1. 比特币/OTS 链上 → **零暴露**；
  2. 公开仓内容/命名（仓库名、`KX…` ticker、每小时 commit 节奏）→ **会暴露**；
  3. 爬虫网络指纹（IP/UA 每小时打 arena）→ **对 arena 自己暴露"有人在读"**。
- **用户倾向说明**：用户对"被反向追踪/关联"极度敏感，此问推动了后续对"秘密到底是什么"的深层反思（见 2.7）。

### 2.7 🔥 重大认知转折 — "追踪本身就是方法"
- **用户纠正（/grill-me）**："追踪 predictionarena.ai 也是一种方法，类似于跟踪伯克希尔/桥水的投资组合。如果我们私有化仓库，只公开 GitHub Pages？"
- **此前误解**：我把"秘密"当成"我们在追踪 arena 这个事实"，拼命设计怎么藏。
- **正解**：用户指出——**追踪动作与追踪对象本身即商业机密（方法/edge）**，类比 13F：持仓公开，但"怎么解析 13F"是基金死守的 edge。故：
  - **必须公开** = 预测方向（Yes/No）+ 最终正确率（营销资产）；
  - **必须死守** = 方法（如何从 arena agent 成交等推导出 Yes/No）。
  - **时间戳用途翻转**：从"隐藏追踪"→"**预注册证明**"（证明每条预测在结算前已发布、不可篡改）。
- **用户倾向说明**：这是全程最关键的指向。用户要的是**敞开成绩单、锁死厨房**——营销靠公开正确率，护城河是私有方法。

### 2.8 纠正后 grill-me 分支 1–5
| 分支 | 用户选择 | 理由与依据 | 用户倾向 |
|---|---|---|---|
| 1 字段粒度 | **接收** `{id,question,call,commit_ts,status}` + 结算 `{actual,correct}`；不公开置信度/赔率/数据源；市场用中性 ID 不挂 `KX…` ticker | 营销要预测+正确率；不挂原始 ticker 避免反向指向 arena 输入 | 接受推荐粒度 |
| 2 发布节奏 | **同意** 每条预测独立 commit（Git 时间戳即存证） | 预注册证明最干净、粒度最细 | 认同"先发证明"价值 |
| 3 正确率维度 | **同意** 总体 + 按类目 | 营销故事更立体 | 认同细分披露 |
| 4 方法论措辞 | **同意** README 一句话带过、不点名 | 高层模糊即可，绝不点名数据源/agent | 认同极简方法论 |
| 5 免责声明 | **同意** 固定 README 顶部 | 合规护栏，模拟盘·非投资建议 | 认同强制 |

### 2.10 仓库数量简化
- **用户要求**："我不想用那么多仓库，管理起来麻烦"。
- **首拟简化**：1 公开仓（forecast-ledger）+ 方法本地化（gitignore，绝不 push）。
- **用户最终选择**：**仍 1 个仓库，但设为私有 + 用 GitHub Pages 发公开脸**。
- **理由与依据**：
  - 1 私有仓 `forecast-ledger` 容纳全部（public-ledger/ + private-method/ + scripts/ + README）→ 方法在私有仓有版本控制；
  - GitHub Pages **只构建 `public-ledger/`**（预测/结算/正确率）+ 生成站点首页，**硬编码排除 `private-method/`** → 公开脸可见、方法永不公开；
  - 仍只管 1 个 repo，管理最省（正是用户诉求）。
- **前置条件（已确认）**：GitHub Pages 从私有仓发布需 **GitHub Pro / Team（或 Enterprise）plan** → **用户确认其为 Pro 版，此路成立**。若免费个人版则需退回"1 公开仓"方案。
- **用户倾向说明**：明确厌恶多仓库管理成本；在"方法无 GitHub 备份"（纯本地）与"1 私有仓+Pages"间，选了后者——既要少仓库、又要方法有私有版本控制。

### 2.11 🔥 决策 — 弃用 OpenTimestamps / 比特币，改用 Git commit 时间戳
- **用户决定**：**不做 OpenTimestamps（锚定比特币）**。存证改为"利用 GitHub 的 Git 记录做存证"——每条预测 commit 即盖时间戳，作为预注册证明。
- **理由与依据**：
  - 用户原话："我们没有计划做这个：每条公开预测在结算前写入账本并打 OpenTimestamps（锚定比特币）。我的计划是利用 GitHub 的 Git 记录做存证。"
  - Git commit 时间戳本身已足够证明"该记录在何时已存在且不可篡改"（内容一旦 commit，SHA 锁死，历史不可改）。
  - 避免引入比特币钱包 / OTS 工具链复杂度，降低维护与合规面。
- **对"可验证性"的诚实表述**：私有仓意味着 Git 历史非公开独立审计；公开可验证性来自**公开页面上的可观测事实**（预测在结算前出现、append-only 不可改），而非"比特币第三方密码学可验证"。叙事文案须据实，不夸大。
- **用户倾向说明**：偏好"够用、简单、自托管式"的存证，反感为"密码学炫技"增加系统脆弱点。

### 2.12 决策 — 营销叙事方向定稿（纯 A "可证明预测"）
- **用户决定**：营销叙事走**纯方向 A**——核心是"可证明的预测 / 提前写、事后对账、命中率公开"，**不混入方向 B**（诚实 scorecard 细节）与方向 C（集体信号 edge，会泄露 method，已排除）。
- **理由与依据**：A 最干净——把"提前公开 + 不可篡改 + 命中率"作为唯一卖点，method 完全隐于架构之后。
- **文风定稿（经多轮迭代）**：参考小米 MiMo 博客（https://mimo.xiaomi.com/zh/blog/mimo-code-long-horizon）的**娓娓道来**风格——口语化、第一人称、设问当钩子、短句多、无清单、无 AI 腔。早期两版被用户判"太 AI / 风格不对"，最终这版认可。
- **用户倾向说明**：极度反感 AI 腔与清单式 dump；要求"说人话"；文风以"像跟人聊天"为准。

### 2.13 决策 — 叙事中点名 Polymarket / Kalshi（但不点名私有信号源）
- **用户决定**：叙事开头与"怎么看账本"段**点名 Polymarket、Kalshi 作为公开预测市场例子**，否则读者不懂"我们在预测什么、答案从哪来"。
- **边界（铁律）**：只点名**市场平台**（问题 + 官方答案来源），**绝不大写/点名私有信号源 predictionarena.ai / agent 追踪方法**。方法仍由架构（私有仓 + Pages 排除 `private-method/`）锁死，文案不破。
- **理由与依据**：读者需要"信息来自哪类市场"的语境；市场平台本身是公开事实，点名无害；而"我们追踪谁 / 怎么推导"是 method，一旦点名即泄密。
- **用户倾向说明**：务实——公开面要给足语境让人看懂，但 method 红线一步不退。

### 2.14 决策 — README 呈现形态（散文 + 轻结构）
- **用户决定**：README 采用「故事开场 + 轻结构支撑」混搭（参考 `0ref/` 中 StockClaw、MiMo-Code、lobehub 的 README 写法），而非纯散文或纯清单。
- **结构（自上而下）**：
  1. 顶部 tagline：`一本公开的预测账本：在答案揭晓之前，先把话撂下。`
  2. 置顶 `[!IMPORTANT]` callout：模拟盘声明（置顶 · 不可删）。
  3. 一句话白话定位（含 Polymarket/Kalshi + 提前写 + 官方结算 + 命中率公示）。
  4. `## 为什么做这本账本`：娓娓道来 prose 全文（一字不动）。
  5. `## 这本账本能做什么`：三栏卡片（提前写下判断 / 官方结算对账 / 命中率公示）。
  6. `## 我们的几条规矩`：五条铁律（提前写不事后改 · 只增不减 · 对账只用官方结果 · 只报命中率不报收益 · 纯模拟无真实下注）。
  7. 工程层：目录结构 / GitHub 仓库策略 / 三条不变式 / 公开预测记录字段。
- **原"## 定位"段移除**：其信息已被"白话定位 + 故事层 + 不变式"完整覆盖，留着重复。
- **用户倾向说明**：认可"故事 + 速读卡片"的配比——人味与可扫读兼得，拒绝纯散文（读者捞不着要点）或纯清单（没灵魂）。

## 3. 最终架构

```
GitHub（仅 1 个私有仓 forecast-ledger）
├── public-ledger/              ← 经 GitHub Pages 发公开脸（营销）
│   ├── predictions/  YYYY-MM-DD.jsonl   {id, question, call, commit_ts_utc, status:"open"}
│   ├── resolutions/ YYYY-MM-DD.jsonl    {id, actual:"YES"|"NO", correct:bool}
│   ├── accuracy.json                       {total, correct, rate, by_category}
│   └── （每条预测 commit 即 Git 时间戳，无需额外收据目录）
├── private-method/             ← 私有仓内，永不进 Pages 构建（方法）
│   ├── tracking/  models/  weights/  alias_map.json  paper_ledger/
├── scripts/                    ← 私有仓内
│   └── scrape / decide / publish_prediction / resolve / accuracy
└── README.md                   ← 免责声明 + 一句话方法论

🌐 GitHub Pages（公开网站，GitHub Actions 自动构建）
   仅取 public-ledger/ → 渲染预测/结算/正确率；❌ 排除 private-method/
```

### 三条不可破的不变式
1. `publish_prediction` 只写 `public-ledger`，**绝不**把 `private-method` 任何内容带进公开面。
2. `scrape` / `decide` 全在私有区，对公开面只输出一个 `call` 字段。
3. 每条预测 commit 即留 Git 时间戳 → 预注册证明；README 顶部免责声明**不可删**。

### 公开预测记录字段（已拍板）
- 预测：`{id, question, call:"YES"|"NO", commit_ts_utc, status:"open"}`
- 结算：`{id, actual:"YES"|"NO", correct:bool}`
- **不公开**：置信度 / 赔率 / 数据源 / 任何 method 痕迹；市场引用用中性 ID，不挂原始 ticker。
- 正确率：总体 + 按类目披露。
- 方法论：README 一句话带过，不点名任何数据源或 agent。

## 5. 未闭环项与风险（对话 review 补充，2026-07-24）

### 5.1 高优先（影响正确率可信度 / 合规红线）
- **结算依据（resolution source）未定义**：`actual` 必须从**市场官方结算结果**（arena/Kalshi 官方 resolution）取得，而非我们自行判断。否则正确率可被"改答案"操纵，预注册证明失去意义。→ 待补：resolve.py 对接官方结算源 + 人工复核。
- **预测不可篡改机制未定义**：预测一经发布（commit 即 Git 时间戳）即**不可修改**；若需修正，必须**新增一条记录**（如 `call_v2`），绝不编辑原行。否则"预注册证明"形同虚设。→ 待补：predictions 文件 append-only 约束 + 修正=新记录规则。
- **模拟盘边界（避免踩"收益率"红线）**：本项目 `AGENTS.md` 禁报收益率。`paper_ledger/` 只追踪**预测正确性（hit/miss）**，**不得计算/披露名义资金盈亏（notional P&L）**。本系统本质是"预测 track record"，不是"资金模拟盘"。→ 待补：明确 paper_ledger 只存 call/correct，不存金额收益。

### 5.2 中优先（运营 / 法律）

- **结算检查节奏未定义**：多频繁检查某市场是否已结算、触发 resolve？→ 待补进 resolve.py。

### 5.3 低优先（确认 / 长尾）
- **题面文本 vs 中性 ID 的张力（确认项）**：我们公开 `question` 原题文本（会暴露具体市场），但不挂 `KX…` ticker。这与"秘密=方法、预测公开"一致（市场本身是公开 arena 数据），属预期行为，非遗漏——仅在此确认。
