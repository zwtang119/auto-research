# ForecastLedger

> 一本公开的预测账本：在答案揭晓之前，先把话撂下。

> [!IMPORTANT]
> **模拟盘声明（置顶 · 不可删）**：本项目为**模拟盘（paper account）**，仅记录预测方向与事后正确率，不涉及任何真实资金下注，不构成投资建议。所披露的"正确率"为预测命中率，**非资金收益率**。

---

ForecastLedger 是一本公开的"预测成绩单"。我们对 Polymarket、Kalshi 这类公开预测市场上正在交易的问题，提前写下 Yes/No 判断；等市场官方结算，再回来对账，并把一路的命中率摊开给所有人看。

## 为什么做这本账本

我们做了一本公开的"预测账本"。

事情的起点其实很简单。像 Polymarket、Kalshi 这样的预测市场平台上，每天都有成千上万个关于选举、产品发布、各种还没发生的事的押注——人们用真金白银，买卖"这件事会发生"还是"不会发生"的合约。每一个这样的问题，到最后都会有一个官方揭晓的答案：发生了，或者没发生。我们一直想弄明白一件事：如果把自己对这些问题的是非判断，老老实实写下来，等结果出来再回头对账，时间长了，到底准不准？

很多人不敢这么做。因为"马后炮"太容易了——答案揭晓之后再表态，谁都能说自己猜对了。所以我们给自己定了一条规矩：判断必须在结果出来之前，公开写上，一字不改，只增不减。

这就是为什么它叫"账本"。每一笔预测，都是一条独立的记录：什么问题、我们押"是"还是"否"、写下的时间。等市场结算，我们再回来，在这一笔下面补上真实的答案，然后标记它对还是错。从第一笔到最新一笔，全按时间排着，谁都能翻。

你可能会问：怎么证明你真的是提前写的，不是事后补的？最直白的证明就在你眼前——每一笔预测，都会在答案出来之前，先出现在这个公开的账本页面上，带着写下的日期，此后一直躺在那里，只会被追加，不会被改动。另外，我们每写一笔都会留一份版本提交记录，提交的那一刻，系统就盖上了时间戳。我们不玩花哨的把戏：公开、留痕、不改。

那这本账本怎么看？它就在我们的公开网站上，谁都能打开。你进来会看到一列预测：每一条都对应 Polymarket、Kalshi 这类公开市场上正在交易的一个问题，写着"我们押是还是否、写下的日期"。市场官方一结算，我们就用那个官方结果回来对账，标出这一笔对还是错。从第一笔翻到最新一笔，全程摊开，没有藏起来的，也没有被删掉的。你甚至可以不时回来看看——新预测总在答案揭晓之前冒出来，旧的那几行，从写下那天起就没动过。

你大概还会想：你嘴上说"写于某天"，我凭什么信那个日期？道理不复杂。账本上的每一笔，背后都是一次提交记录——我们把它交到版本库的那一刻，系统就记下了当时的时间，这个时间是改不了的。公开网站上的内容，正是从这些提交记录里一点点长出来的。所以你看到的日期，不是我们事后填的，而是那条记录真正诞生的时间。我们不做"先有答案、再补日期"这种事，因为那样做，提交记录会对不上，一查就露馅。

最后说清楚一件事：这是一本"模拟账本"。里面没有任何真实的下注，不牵涉一分钱，我们也不给任何人投资建议。它更像一份长期的自证——我们到底有没有判断力，时间会替我们回答。

## 这本账本能做什么

| 提前写下判断 | 官方结算对账 | 命中率公示 |
| --- | --- | --- |
| 在每个问题结算前，公开写下我们对"是/否"的判断，带日期、只增不减。 | 市场官方一结算，就用官方结果回来对账，标出这笔对还是错。 | 总命中率与分类目命中率全程摊开，所有人可查。 |

## 我们的几条规矩

- **提前写，不事后改**：判断在结果出来前公开落笔，一字不改。
- **只增不减**：账本是 append-only，修正等于新增一条记录，绝不涂改旧行。
- **对账只用官方结果**：以市场官方结算为准，不自判答案。
- **只报命中率，不报收益**：我们只晒预测准不准，从不算、也不报资金收益率。
- **纯模拟，无真实下注**：里面没有任何真实下注，不牵涉一分钱。

## 目录结构

```
forecast-ledger/
├── public-ledger/           # 推到私有仓 forecast-ledger；经 GitHub Pages 发公开脸
│   ├── predictions/         # {id, question, call, commit_ts, status}
│   ├── resolutions/         # {id, actual, correct}
│   └── accuracy.json        # {total, correct, rate, by_category}
├── private-method/          # 私有仓内（方法）；不进 Pages 构建，永不公开
│   ├── tracking/            # 信号源抓取/解析
│   ├── models/              # 如何推导 YES/NO
│   ├── weights/             # 阈值 / ensemble
│   └── paper_ledger/        # 模拟盘估值（仅模拟）
└── scripts/                 # scrape / decide / publish / resolve / accuracy（私有仓内）
```

**GitHub 仓库策略（最终 · 用户拍板）**：**仅 1 个私有仓 `forecast-ledger`** + **GitHub Pages 发公开脸**。
- 整个项目（`public-ledger/` + `private-method/` + `scripts/` + README）推到这一个**私有仓**，方法在私有仓内也有版本控制。
- GitHub Pages **只构建 `public-ledger/`**（预测/结算/正确率）+ 生成的站点首页，**绝不纳入 `private-method/`** → 公开脸可见，方法永不公开。
- 仍只管 **1 个 repo**，管理最省。
- ⚠️ 前置条件：GitHub Pages 从私有仓发布需 **GitHub Pro / Team（或 Enterprise）** plan；若账号是免费个人版，此路不通，退回「1 公开仓」方案（public-ledger/ 公开、private-method/ 留本地）。

## 三条不可破的不变式

1. `publish_prediction` 只写 `public-ledger`，**绝不**把 `private-method` 的任何内容带进公开仓。
2. `scrape` / `decide` 全在私有区，对公开仓只输出一个 `call` 字段。
3. 每条预测 commit 即留 Git 时间戳 → 预注册证明；README 顶部免责声明**不可删**。

## 公开预测记录字段（已拍板）

- 预测：`{id, question, call:"YES"|"NO", commit_ts_utc, status:"open"}`
- 结算：`{id, actual:"YES"|"NO", correct:bool}`
- **不公开**：置信度 / 赔率 / 数据源 / 任何 method 痕迹；市场引用用中性 ID，不挂原始 ticker。
- 正确率：总体 + 按类目披露。
- 方法论：README 一句话带过，不点名任何数据源或 agent。
