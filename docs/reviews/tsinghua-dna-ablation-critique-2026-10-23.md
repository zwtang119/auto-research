## 2. 发现与精确修正

### F1｜中：分摊 token 的类型与计算式矛盾（baseline 继承）

**位置**：P:358–366、P:379–386；E:654–678。

Green Source：P 把 token 一概定义为 nullable integer，却把 `generation_tokens_allocated` 定义为企业尝试 token 加摘要 token 的 1/3。摘要总 token 不被 3 整除时该列必为小数，强转整数会丢失总量。

**精确修正**：P:365 改为“`run_id`、计数、原始 token 字段为 nullable integer；`generation_tokens_allocated` 为 nullable number，保留分数分摊精度，不逐行取整”。codebook 写明批内三企业分摊和应等于企业请求总量加摘要总量（浮点比较有固定容差）；任一相关 usage 未知时按现有 NA 规则处理。验收例：摘要 10 tokens，三企业各分摊 10/3，而不是各取 3。

### F2｜高：unknown 与已落盘响应之间缺少恢复裁决，SASR RNG 恢复也未规定（baseline 继承）

**位置**：P:244–279，特别是 P:254、274–278；P:94–96、P:603–604。

Green Source：响应原子落盘先于成功事件；进程死亡且无终态又一律记 unknown；恢复仅笼统说继续未完成逻辑调用。由此存在“响应已 rename、成功事件尚未追加”的窗口：若只按事件恢复，会再次发送已收到的请求。MAMR checkpoint 明列 RNG，SASR 及跨任务的 `(condition, model)` RNG 游标没有同等约定。

**精确修正**：在 P:274 后加入确定恢复顺序：
1. 先按 attempt ID 查 durable response，验证请求/响应哈希与 revision；若有效，补写成功事件及 checkpoint，不重发。
2. 只有无可验证响应的 prepared 才转 unknown。unknown 计入该逻辑调用已用发送次数，其费用预留不因后续成功而自动释放；只有账单核销或可证实未收费才冲回。
3. 显式恢复允许在剩余传输次数内新建 attempt；沿用同一逻辑调用及相同请求体，不把 unknown 变成一次新的内容尝试。额度耗尽保持 incomplete。
4. SASR/MAMR 均在首次发送前持久化实际请求体、framework/context 选择、RNG 前后状态和任务游标；恢复复用已准备请求，不重新抽模板。完成任务被跳过时恢复对应已消费 RNG 状态。

补充 mock 验收：分别在 prepared 后、response rename 后、success event 后强制中断；验证成功响应不重发，unknown 计数不重置，恢复后剩余 prompt 序列与无中断执行一致。这里是未来验收要求，本轮未运行。

### F3｜高：网关/model ID 冻结不等于上游路由冻结（baseline 继承）

**位置**：P:157–203、P:229–239、P:578–580、P:685。

Green Source：配置只给 OpenRouter/Paratera 与请求 ID；返回字段允许 `upstream_provider=null`，版本恢复规则只比较本地哈希，没有上游 provider、模型版本/量化、fallback 策略或漂移处置。计划也明确承认路由混杂（P:442）。因此本地配置不变时仍无法按本文判定“同一正式臂没有混入不同定义”。

**精确修正**：在 §3.3 增加 `routing_policy`，冻结每个角色的请求模型 ID、endpoint、可支持的上游 allowlist/指定路由、fallback=false 及可获得的版本/量化标识；授权后的 G2 确认能力，G1 只 mock 校验。每请求将实际路由与冻结策略比较，明确漂移即停止该路由后续派发，保留已收响应并标异常。网关不支持锁定或不披露时，不伪造固定值：默认 G2 不通过“上游已冻结”项，需在运行前明确批准“动态/不可观测路由、仅冻结客户端策略”的已披露例外。不得将模型替换或自动 fallback 当恢复。

这不要求五月上游同一性证明，也不扩臂；五月 DeepSeek=0423 继续仅标用户确认。新增 §3.2.1 的无搜索配置也须纳入同一最终请求策略哈希。

### F4｜高：Paratera 配额授权与全局费用熔断相冲突，smoke 未计入该基础范围（整合后未闭合）

**精确修正**：
