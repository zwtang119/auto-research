## 3. The Protocol

### 3.1 设计问题：一次性 benchmark 的三种死法

事前预测（ex-ante forecast）的同台比较在概念上只需三样东西：冻结的预测、冻结的赛果、冻结的评分规则。然而对 2024–2026 年间公开报告的预测评估做一次事后复盘，会发现失败极少来自评分规则本身，而来自三样"冻结"各自以不同方式悄悄解冻：

1. **快照漂移（snapshot drift）**。声称"赛前"的数据文件在赛后被重新生成，文件头部的 `generated_at` 随每次管线重跑前移。本文数据集中即存在两个实例（§4.2）：`odds.json` 的工作区版本相对其赛前 commit 发生漂移（match 1 主胜概率 0.7629 → 0.7004）；市场基线中阿根廷与巴西的前五末席之争在两个相隔两天的快照间反转（差 0.19 个百分点），导致"市场前五是否包含亚军"这一事实性问题的答案取决于快照日期。若评估者取用了错误的版本，没有任何下游统计能发现这一点。
2. **预注册缺位（preregistration absence）**。分析协议在看过结果之后冻结，凡与结果一致的口径被保留，不一致的被修正。其极端形式甚至不需要恶意：本文数据集的夺冠概率在赛前曾进行过一次归一化修正（commit `875748b`），修正改变了头号热门——这一修正发生在赛前、动机正当，但它提醒：在没有任何冻结纪律时，"赛前预测"与"赛前方法论"是两个可以被分别修改的东西。
3. **来源渗漏（source leakage）**。声明为"独立"的预测信号实际共享上游数据。本文数据集中，一个 LLM 群体信号经 Elo bonus 通道渗入另一统计基线，使两条"考生"在来源上不再独立（§5.4，PIV 的 `source_integrity` 字段将该污染显式标注为 `red_contaminated`）。

这三种死法的共同点：它们都不在分数里留下痕迹。一个评估可以拥有正确的 Brier、漂亮的 reliability 图，同时其输入版本是漂移的、其分析口径是事后挑选的、其两条基线是同源污染的。**分数的完备性不能替代协议的完备性**——这是本协议的设计出发点。

### 3.2 五件套：定义与设计理由

协议由五个相互咬合的组件构成（图 1）。每一件单独看都有先例；将其作为**缺一不可的最小闭集**提出，是本文的方法学主张：

**（i）git 冻结（content-addressed freezing）**。一切评估输入（预测、赛果、基线、分析代码）以 git commit 哈希寻址。选择 git 而非"文件 + 日期"，因为 commit 哈希是内容寻址的：任何字节的改动都会改变哈希，完整性校验退化为一次哈希比对。但 git 层有一个必须明说的边界：commit 的作者日期与提交日期是**自声明字段**，可被倒签。因此 git 冻结只解决"内容不可改"，不解决"时间不可伪造"——后者由审计链（§3.4）补齐。

**（ii）来源分级（source tiering）**。每条进入因子账本或预测管线的信息携带来源等级（Green / Yellow / Red）。Green 级（可独立核验的原始事实，如官方赛果）方可作为事实输入；Red 级（舆论、聚合情绪、未核验转述）只能作为基线或叙事材料，且其流向必须被追踪——来源分级的目的不是"只用好来源"，而是**让污染可见**：当 Red 级信号渗入另一条基线时，该基线的 `source_integrity` 字段必须改标，而不是装作独立（MCDP-1 边注：来源边界是审计结果的一部分，而非附属标签）。

**（iii）统一结算（uniform settlement）**。所有预测者在同一结算管线下对账：同一赛果版本（Green Source 核验）、同一指标族（RPS 主指标 + Brier 全分与 Murphy/Yates 分解 + Log Loss + reliability 分箱）、同一覆盖归一化规则（各预测者覆盖队伍数不同时，只在交集上比较，分母逐任务显式报告）。统一结算消除的是"各自评分、各自报喜"的自由度。

**（iv）OSF 分析协议冻结（analysis-protocol freezing）**。指标定义、比较族、多重比较校正、判定规则在分析执行前冻结于 OSF（开放科学框架）。本研究的诚实边界在此：分析协议冻结发生在赛后（作者已见部分结果），因此我们不使用 "pre-registered" 一词；冻结的价值不在于"预见"，而在于**此后不得再改**——凡冻结后的口径调整均以修订记录留痕（§7）。

**（v）协议完整性向量（Protocol Integrity Vector, PIV）**。上述四件的状态，逐预测者、逐字段显式标注（§3.3）。PIV 是本协议与既有实践的分界线：它不是附属的合规清单，而是与预测分数**并列的一等评估字段**——一个 Brier 最优但快照漂移的预测者，在协议的读法下不优于一个分数次优但全字段合规的预测者。

### 3.3 PIV：字段定义与处置规则

PIV 为每个被评估对象（预测者 × 任务层）标注八个字段（表 1）：

| 字段 | 取值 | 含义 |
|---|---|---|
| `ex_ante_status` | valid / invalid / unknown | 预测是否可证明先于事件 |
| `snapshot_status` | immutable / commit_recoverable / drifted | 评估用文件是否为其冻结版本；drifted 时必须从版本史提取（本研究对 `odds.json` 即按此处置，取 commit `88a9bfd` 版本） |
| `source_integrity` | green_only / red_contaminated / mixed | 上游来源是否发生跨级渗漏 |
| `prompt_hash_status` | valid / placeholder | LLM 类预测者的提示词是否哈希固定（placeholder 指无法排除提示词事后调整） |
| `schema_status` | pass / fail(+violation IDs) | 数据是否符合声明的 schema；失败模式可用于解释结构异常（见 §5.2 的 rank-vs-mass 分裂案例） |
| `adjudication_status` | independent / same_author / absent | 结算是否由独立于预测作者的一方执行 |
| `baseline_coverage` | n/N | 该预测者在任务层的实际覆盖分母（禁止以"全量"措辞掩盖部分覆盖） |
| `preregistration_status` | executed / missed / post_hoc | 分析协议冻结的时态 |

两条处置规则使 PIV 成为操作而非装饰：

- **fail-loud**：任何字段无法判定时取最保守值（unknown / post_hoc / absent），不允许静默留空。评估者必须"响亮地失败"，把不可判定本身作为报告内容。
- **并列报告**：每张结果表必须同时呈现预测分数与 PIV 字段（§5.4 表 1 即按此格式）。读法由此改变——"谁更好"从单轴排序变为二维状态。

PIV 的诊断力在 §5 中以两个层面检验：(i) 描述性验证——已知结构失败（如 P3 的 rank-vs-mass 分裂、P1 的同源污染）能否由字段取值解释；(ii) stretch 目标——字段 taxonomy 冻结后在三个公开预测 artifact（WorldCupBench / Prophet Arena / ForecastBench）上做双人盲标注，Cohen's κ ≥ 0.6 则字段具备外部生存性；κ 不达标则 PIV 降级为内部应用并如实表述（预写降级路径，不影响 H1–H4）。

### 3.4 审计链：给"冻结"加上不可伪造的时间

git 冻结管内容，审计链管时间。审计链按**时间戳的伪造难度**分三级，逐级独立于作者：

- **L1 自声明层**：git author/committer date。可倒签，单独不足为凭，仅作内容寻址索引。
- **L2 平台服务端层**：GitHub Actions 运行记录与 Events API。运行记录由平台在工作流执行时生成，将 commit 哈希与服务器时间戳绑定；仓库作者对该数据库无写权限。本研究的审计链含 148 条运行记录（最早 2026-06-11T06:28:03 UTC，开赛日）。特别地，部分关键 commit 由定时工作流（github-actions[bot]）生成——定时任务不可能先于其执行时刻存在，此类 commit 的"出生时间"即为服务器时间，倒签在机制上不可能。L2 记录受平台保留期约束（本研究已设为 400 天），故配套导出件 + 字节级校验和清单作为保全副本。
- **L3 独立第三方层**：邮件服务商时间戳（GitHub 系统通知邮件，Google 服务器盖章，与 L2 记录分钟级互证）、公开网页存档（Internet Archive）、以及区块链与 RFC 3161 可信时间戳（OpenTimestamps 双日历提交 + FreeTSA，锚定对象为全量证据的 SHA-256 清单）。L3 的作用是在 L2 随平台保留期衰减后，保全"该哈希最晚于某日已存在"的不可改证据。

设计纪律：任何一条时间主张在文中必须能归入且只归入上述一级，并以该级的措辞报告（§7 的禁用表述对照即按此执行）。全部证据物（bundle、导出件、截图、校验和、锚定收据）的复现与核验入口见 §7 Data Availability。

### 3.5 与既有实践的关系

本协议与三类既有实践的关系需要显式划清，以免被读成重命名：

- **OSF 预注册**：预注册冻结的是"假设与分析计划"，本协议的 OSF 组件只冻结分析协议；其上游三件套（git 冻结、来源分级、统一结算）处理的是预注册鞭长莫及的输入层（版本、来源、结算）。预注册不能保证输入未漂移，正如本文的漂移实例所示。
- **预测锦标赛平台（GJP、预测市场）**：平台天然执行统一结算与真实时间戳，但其协议内嵌于平台自身，不可拆分为可移植组件；本协议面向的是平台之外、由研究者自行采集的多源预测——那里恰是三种死法的高发区。
- **Forecast reconciliation（Hyndman 谱系）**：本文的 "reconciliation" 与层次预测文献中的 reconciliation（聚合一致性调整）含义不同：本文指**多预测者在统一审计链下的对照阅卷**（reconcile the *evaluation*），而非对预测值本身做层级调整。二者处理的问题正交，方法上可组合（先以本文协议审计输入，再以 Hyndman 方法调整输出），但不互相包含。

由此，知识缺口可精确陈述：任务层（世界杯预测）、指标层（proper scoring）、benchmark 形态均已被占据；**协议审计粒度**——把冻结、来源、结算、时态的完整性状态作为一等评估字段——在本文的定向核查范围内未被占据（系统检索见 §2，为本文的 Check 4 闸门）。
